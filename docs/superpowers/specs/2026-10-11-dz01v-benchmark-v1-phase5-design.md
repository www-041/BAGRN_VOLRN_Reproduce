# DZ01V Benchmark V1 Phase5 design — six-method single-pair translation development

Status: written design for researcher review. Approval of this file precedes the implementation plan and code. No Phase5 method result is asserted here.

## Purpose, scope, and frozen authority

Phase5 builds an independent six-method registration adapter and a DEVELOPMENT-only single-pair runner. It prepares, but does not automatically run, the four-pair comparison. The four frozen trial pairs are `00_01`, `02_03`, `05_07`, and `08_10`; their 43 DEVELOPMENT, 84 pending-second-review TEST, and 33 UNASSIGNED points retain the Phase3 roles. Phase3's EPSG:32650 origin `(0, 0)` m, 10 km cells, 500 m safe-core buffer, role formula, and every candidate/review/input hash remain unchanged. Full 15-pair and 13-scene global-network evaluations are outside this phase.

Phase5 may read the eight B9 image paths and hashes from the frozen Phase3/Phase4 manifest and the 43 approved DEVELOPMENT points through `load_development_truth()`. The matcher process receives **no** candidate CSV, split-assignment CSV, TEST coordinate, human label, second-review file, or DEVELOPMENT truth. A separate evaluator may open only the frozen DEVELOPMENT truth after the estimated transform has been persisted. No manual point, including DEVELOPMENT, may be substituted for a matcher correspondence or used in the final transform fit. Evaluation and parameter-tuning decisions are logged; the pending TEST set is never evaluated in this phase.

Implementation is confined to a new `src/benchmark_v1_phase5/` package, a new single-pair script and config, new Phase5 tests, and `docs/benchmark/v1/phase5/`. Existing Task15/Task16, `src/registration_benchmark/`, original imagery, Phase1–4 artifacts, and formal outputs are read-only. The current workspace is already a linked worktree; changes must not touch the parallel radiometric R1 worktree/files/environment. Do not install packages into `.venv-registration` to enable KARIOS or AROSICS. Phase5 does not commit or push parallel work implicitly.

## Method registry and environment audit

The main comparison has exactly six method IDs: `SIFT`, `KARIOS`, `AROSICS_GLOBAL`, `LoFTR`, `EfficientLoFTR`, `LightGlue+DISK`. The first, second, fourth, fifth, and sixth output correspondences. `AROSICS_GLOBAL` uses its native `COREG` global translation; `COREG_LOCAL` is a separate future local-model experiment and never enters this ranking. Prefer thin wrappers around existing repository SIFT/LoFTR/EfficientLoFTR/LightGlue+DISK implementations without changing them. KARIOS and AROSICS are invoked through isolated, documented environments or subprocesses with explicit input/output files. Do not substitute another algorithm when an environment is missing.

Record per method: installed distribution and version, official source revision where used, weight identity and SHA256 where applicable, runtime/Python environment, input-grid requirements, coordinate/output semantics, dependency and license evidence, and a readiness category. `IMPORTABLE` is not `END_TO_END_VERIFIED`. For KARIOS and AROSICS, successful isolated-environment setup and a synthetic sign/coordinate test are prerequisites to a real-data smoke attempt. If installation or licensed weights are unavailable, report `ENV_UNAVAILABLE` or `WEIGHTS_UNAVAILABLE` with cause; preserve a future run slot rather than fabricate output. The audit must distinguish methods validated end-to-end from adapters tested only with synthetic stub output.

## Common input and provenance

Before any method runs, construct one immutable *pair input descriptor* from the frozen B9 files: scene identities and SHA256, native affine/shape/CRS, band, true valid masks (`read_masks(1)>0` plus finite/no-data checks), predeclared geometric intersection, overlap grid, crop windows, normalization/display transforms, and resize transforms. The overlap geometry derives only from georeferencing and valid support, never from matcher scores or Phase4 transforms. Reject wrong identity, unsupported CRS/grid, non-finite affine, and no true shared valid support. A bounding-box intersection alone does not establish overlap. Use bounded windows/tiles rather than allocating the full union mosaic. Every method receives the **same** pair descriptor and declared overlap region; method-specific model input normalization may be required but must be recorded and cannot alter the evaluated geographic footprint or valid-mask eligibility. KARIOS's same-grid requirements are met by the common declared pair view, not by a hidden alternative crop. No method receives the old Task15 EfficientLoFTR solution as initialization.

Input pixels are identified by their native **pixel-center** `(row, col)` coordinates (zero-based; raster affine acts on `(col+0.5, row+0.5)`). The common-grid view and any resized model view each store a reversible map from view pixel center to projected coordinates, and projected coordinates map to each image's native pixel center. On return, each correspondence is converted to `scene_i` and `scene_j` native coordinates separately. Reject non-finite, masked, out-of-window, or invalidly mapped points. Record every crop, stretch, resampling kernel, resize factor, and inverse mapping. Input radiometric stretch is only for matching and never overwrites B9 data.

## Common two-dimensional translation contract

The published Phase4 contract remains the external result format: native `(delta_row, delta_col)` in `scene_i -> scene_j`, in pixel units, with complete native origin offset, not merely a common-grid residual. For every native correspondence, define `d_k = (row_j-row_i, col_j-col_i)`. SIFT, KARIOS, LoFTR, EfficientLoFTR, and LightGlue+DISK feed such correspondences into one predeclared robust 2D-translation estimator: deterministic seed; minimum usable-match count; fixed inlier distance in native pixels; fixed iteration/stopping rule; method-independent inlier computation; final componentwise robust center of inlier displacement; and explicit failure if support or spatial coverage is insufficient. Freeze the exact numeric values in the implementation plan/config **before** running `00_01`; never tune them to favor one method. Method confidence is internal provenance, not a common cross-method quality scale. Match/inlier counts and overlap-grid coverage are reported, with `not_applicable` for direct-shift methods.

AROSICS `COREG` supplies a direct shift. Record its selected window and native internal registration procedure, raw shift, unit, direction, and conversion to the same full native `scene_i -> scene_j` translation. Do not invent correspondences or apply the shared correspondence estimator to it. The main table compares final global translations under common inputs and evaluation, **not** feature extractors isolated from all solver differences. An AROSICS shift sign or pixel-center convention that cannot be proved by known-translation synthetic data blocks its real-data result.

Where native image grids differ only by translation, the estimated map must include georeferenced origin differences. If affine scale/rotation mismatch means a single native-pixel translation cannot represent the pair mapping, return `UNSUPPORTED_GRID` rather than silently fit an affine or conceal the mismatch. Leave an extension seam for future scene-graph edges (`pair_id`, direction, transform, uncertainty/provenance), but implement no global network or cycle optimization.

## Status, evaluation, and output semantics

Keep execution and evaluation states separate. Execution states are `NOT_ATTEMPTED`, `ENV_UNAVAILABLE`, `WEIGHTS_UNAVAILABLE`, `NO_VALID_OVERLAP`, `UNSUPPORTED_GRID`, `ALGORITHM_FAIL`, and `SUCCESS`. Evaluation states are `NOT_EVALUATED`, `NO_INDEPENDENT_TRUTH`, `EVALUATED`, and `INVALID_RESULT`. Only `ALGORITHM_FAIL` means an attempted algorithm failed; absent truth never changes an execution `SUCCESS` into failure. Exceptions are recorded with bounded diagnostics, not swallowed. Every requested method/pair has a row; no successful-only denominator. AROSICS matching/inlier counts are explicitly not applicable. Write new Phase5 outputs atomically and refuse to overwrite existing output roots without a deliberate resume rule.

Only after transform persistence does the isolated scorer load frozen DEVELOPMENT truth. It rejects any TEST/UNASSIGNED row and any non-normalized transform. For each DEVELOPMENT point, predict `(row_i+delta_row, col_i+delta_col)` and compare against native scene-j coordinates; Euclidean pixel error gives RMSE, P95, maximum, and PCK@1/2/3 px. Report per-pair counts, method status and success-only pair macro metrics with attempted/failure denominators. These are DEVELOPMENT diagnostics, not independent final TEST or published generalization accuracy. Preprocessing, algorithm/solver and evaluation wall times are separate; peak RAM/VRAM are included only when their measurement scope is reliable, otherwise `UNKNOWN` with reason. Environment and numerical warnings are retained.

Each output records code revision/dirty state, input hashes, config hash, seeds, method/weight versions, complete preprocessing chain, valid-overlap count/extent, coordinate convention, estimator parameters, transform, counts, metric definitions, timings, exception, and the exact scope label `FOUR_PAIR_DEVELOPMENT_PREPARATION` or `SINGLE_PAIR_00_01_SMOKE`. No candidate point coordinates appear in the matcher-input artifact. Formal TEST export remains governed by Phase4 and is not called here.

## Verification and controlled execution

First audit interfaces/dependencies/weights/licenses without model inference. Next use small synthetic GeoTIFFs with known positive and negative subpixel translations, unequal native origins, crop/resize, NoData holes and no-overlap cases to verify every available adapter's sign, center convention, mask rejection, full-native offset, common estimator and scorer. An absent dependency is an explicit skip/unavailable status, not a synthetic end-to-end pass. A direct-shift AROSICS adapter gets a contract test with synthetic output even if the package is absent; the real library's sign must be separately verified before claiming it ready.

The sole authorized real-data attempt in this phase is an explicitly bounded `00_01` smoke. Its command selects one method at a time, caps overlap view size, memory/runtime and GPU usage, and writes only under `docs/benchmark/v1/phase5/` (or a dedicated Phase5 output root). It records the method(s) actually attempted and any skips/failures. It must not auto-loop all six methods, all four pairs, or launch Task15/Task16. Smoke metrics, if DEVELOPMENT truth is scored, are labeled exploratory, never a formal Benchmark result. The four-pair command/config is prepared and printed for the researcher; no four-pair execution occurs in Phase5.

Target deliverables are: adapter status and version/environment reports; shared-input and geometry output protocol; four-pair DEVELOPMENT config and explicit manual PowerShell commands; synthetic and `00_01` smoke logs; tests; and Phase5 readiness report. Run focused tests, full `pytest`, `compileall`, and `git diff --check`; disclose every failure, skip, dependency gap, and untested method. Stop after the bounded smoke and await the researcher's decision on the four-pair run.
