# DZ01V Benchmark V1 Phase4 design

Status: design for review. This document does not assert that Phase4 code or real second reviews exist.

## Purpose and fixed inputs

Connect the frozen four-pair Phase3 split to an independent human second-review workflow and prepare, but do not run, six registration adapters. The 160 original candidate rows, first-review history, eight verified B9 inputs, and all Phase3 files remain read-only. In particular, the EPSG:32650 origin `(0, 0)` m, 10 km cell, 500 m edge margin, `(ix + 2*iy) % 3` role formula, and 43 DEVELOPMENT / 84 TEST candidate / 33 UNASSIGNED assignments are immutable. The full 15-pair benchmark remains unfrozen.

The current annotator's `CandidateReviewStore.review()` and `save_candidate_session()` mutate the source candidate CSV, so Phase4 must never call them from second-review mode. Its optional `--frozen-split` reads polygons, not the authoritative Phase3 assignment CSV. An independent mode is required.

## Read-only join and freeze validation

On opening a trial pair in `scripts/annotate_benchmark_v1.py --second-review`, load `docs/benchmark/v1/phase3/checkpoint_split_assignments.csv`, `split_leakage_audit.json`, and the pair's source candidate CSV. Resolve defaults relative to the repository root, never the PowerShell current directory. Join on the exact tuple `(pair_id, candidate_id)`, require 40 unique rows per pair and 160 unique rows in the full assignment file, and require the recorded 43/84/33 role counts. Reject missing, duplicate, extra, or mismatched scene IDs. Recompute the SHA256 of all four candidate CSVs and every Phase3 artifact listed under `output_sha256` in the audit; require exact matches. Verify the eight B9 hashes already recorded in the audit before any formal export. No GUI fallback to an unverified split is allowed.

Display the Phase3 role and global cell ID as immutable labels. The existing editable Split combobox is disabled/hidden in second-review mode. UNASSIGNED and DEVELOPMENT points may be displayed for context but cannot receive a TEST second-review decision. The only first-review source accepted for an exportable TEST point is an original `human_review_status=APPROVED`, a nonempty first-reviewer identity, and unchanged source-coordinate/review fields matching the Phase3 snapshot. A SHA mismatch is a hard stop, not a warning.

## Independent second-review events

Second-review mode uses a separate per-pair append-only JSONL event file under `docs/benchmark/v1/phase4/second_reviews/`. No real event files are initialized with synthetic approvals. Each event contains schema version, pair/candidate IDs, frozen Phase3 role/cell, exact Phase3 and source SHA256 references, event UUID, prior-event hash (for sequence checking), UTC timestamp, reviewer identity, explicit confirmation of independent visual inspection of *both* original-resolution image locations, outcome (`APPROVED`, `REJECTED`, `DOUBTFUL`), optional adjustment reason, first-review coordinates, proposed second-review pixel and projected coordinates for both images, coordinate-difference diagnostics, reviewer-declared disagreement (`YES`/`NO` with explanation), and separate machine-derived spatial-validity status and exclusion reasons. The original first-review decision and confidence appear in the stored audit snapshot but are hidden by default in the second-review GUI. Candidate score remains explicitly non-accuracy metadata.

An adjustment does not rewrite or erase earlier events. Its first attempted geometry and every later correction stay in the log. A point with any recorded out-of-safe-core, different-cell, or cross-role isolation violation is permanently `NOT_ELIGIBLE_AFTER_COORDINATE_ADJUSTMENT` for this freeze, including after another adjustment returns to the original coordinates. Its frozen `TEST` role remains unchanged. Any reviewer-declared material disagreement enters `DISPUTE_PENDING`; no automatic best-coordinate selection or automatic dispute resolution is provided in Phase4. Events must not claim a real person has reviewed a point merely because a name string was supplied; the GUI requires explicit human actions, records the entered identity and the confirmation, and the readiness report notes that software cannot authenticate a person's real-world identity.

Before saving a second-review event, require the second reviewer to be nonempty and different from both the first-review `primary_reviewer` and the original `reviewer`. An `APPROVED` action requires explicit confirmation of left and right inspection and a new human localization-uncertainty statement; it cannot inherit HIGH confidence or the first ±0.5 px note. REJECTED and DOUBTFUL remain valid records but never truth. The GUI displays TEST pending, approved-and-spatially-valid, doubtful, rejected, ineligible-after-adjustment, and dispute-pending counts, each derived from the latest event plus sticky disqualification history. The source candidate CSV, Phase3 CSV/GeoJSON/audit, and first-review truth CSV are opened read-only and rehashed after a session.

Coordinate checks use native pixel-to-projected transforms from the two B9 headers. Both final effective positions must be strictly inside the *original frozen* cell's 500 m inset, remain in the same cell, lie on valid image support, and remain at least 1,000 m from every assigned DEVELOPMENT point using both images' projected coordinates. No role reassignment occurs. A failed geometry check is recorded separately from the human outcome: even an explicit human APPROVED event cannot make such a point scoreable.

## Formal TEST export gate

Create a read-only validation/export command that joins the frozen rows, immutable source candidates, latest second-review events, and a development-use ledger. For each of the 84 TEST candidates, emit either one formal truth row or an exclusion row with explicit reason codes. Eligibility requires all of: exact frozen identity/hashes and eight B9 identities, frozen TEST role, valid first approval, distinct second reviewer and explicit APPROVED event, complete inspection/uncertainty statements, valid final native-pixel and projected coordinates in the original safe core, valid image masks, no persistent adjustment violation, no unresolved coordinate dispute, cross-role spatial isolation, and a signed research-run declaration that TEST point IDs and coordinates were excluded from model fit, RANSAC selection, threshold choice, and tuning. The tool cannot independently prove historical non-use; absent or inconsistent declaration is a hard gate. Rejection, doubt, no event, duplicate/replayed event, conflicting hash, or missing input is excluded, never silently dropped. No real TEST truth rows are generated by development tests.

The formal TEST exporter and evaluator must use this validated output, not `CandidateReviewStore.approved_truth()`, a generic `split=TEST` CSV field, or unreviewed candidates. Keep an exclusion report by pair and reason. DEVELOPMENT truth export uses only the 43 frozen DEVELOPMENT points and never loads TEST coordinates into the fitting/parameter-selection interface.

## Six-method DEVELOPMENT adapter contract

Prepare one four-pair manifest and one result schema for SIFT, KARIOS KLT, AROSICS `COREG` global translation, LoFTR, EfficientLoFTR, and LightGlue+DISK. AROSICS `COREG_LOCAL` is an optional separate local-model experiment and is not in the common translation ranking. Each adapter consumes the same frozen pair IDs, B9 input identity, native-grid/mask convention, and explicit preprocessing transform chain. It returns a final 2D translation mapped to native pixel coordinates, `SUCCESS` or `FAIL` with reason, elapsed time, and provenance. A failed or missing method/pair occupies a row with null metrics. The DEVELOPMENT-only evaluator computes RMSE, P95, PCK@1/2/3 px and per-pair/macro summaries from independent DEVELOPMENT points; it never opens second-review files or scores the 84 pending TEST points. Interface tests use synthetic images/transforms and deliberate FAIL records; they do not launch six real methods. KARIOS and AROSICS are currently not installed in the local `.venv-registration` environment and must remain `NOT_VERIFIED_END_TO_END`, not PASS. Existing SIFT, LoFTR, EfficientLoFTR, and LightGlue+DISK adapters are inspected for contract compatibility, but importability alone is not an end-to-end result.

## Deliverables and tests

Deliver a separate second-review policy/storage module, the `--second-review` GUI path, a formal TEST export/validation interface, a DEVELOPMENT adapter/result-schema and synthetic runner, PowerShell usage instructions, schema documentation, and `docs/benchmark/v1/phase4/benchmark_phase4_readiness.md`. Do not overwrite Phase2/Phase3 files or real experimental outputs.

Focused synthetic tests must cover frozen join counts/hashes and deliberate mismatches; distinct reviewer and explicit dual-image inspection; save/reload and append-only event history; valid adjustment inside the same safe core; edge, other-cell, invalid mask and cross-role isolation failures; sticky ineligibility after any invalid adjustment; APPROVED human outcome with failed spatial validity; REJECTED/DOUBTFUL/disagreement exclusions; exclusion reason accounting; DEVELOPMENT-only access and scoring; FAIL preservation; and no actual second-review events or official matcher runs. An auxiliary GUI smoke test uses disposable synthetic review storage and verifies the source files' SHA256 are unchanged. The final report states that all 84 real TEST candidates remain awaiting independent review unless actual human events have been supplied later.
